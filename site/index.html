The lifecycle, as a system of record

Security teams rarely lack scanners. They lack one place where every scanner's output, every asset and every piece of business context meet — and where “fixed” means verified rather than asserted.

Scope→Discover→Inventory→Assess →Prioritize→Attack paths→Remediate→Retest

How it is built

Authorized by construction

No engine touches a target that isn't covered by a recorded authorization. Active techniques and private networks need their own flags, re-checked at run time.

Evidence over assertion

Findings carry stored evidence and a confidence level. One closes only on a retest that no longer observes it, or a recorded manual verification.

Transparent risk

Likelihood × impact, with contextual escalators and KEV floors. Every score keeps its full breakdown, so a ranking can always be explained.

Isolation in the database

Multi-tenancy is enforced by PostgreSQL row-level security under a role that cannot bypass it — not only by application code.

Attack paths

Shortest exposure chains from internet-facing entry points to critical assets, over evidence-backed relationships, graded verified, probable or theoretical.

Honest coverage

Every integration states what it was verified against, and the limitations are published rather than hidden.

AI systems are assets, not a separate product

  • Discovery. 51 AI technologies: providers, frameworks, vector databases, serving runtimes and MCP SDKs — found from imports, dependencies, endpoints, containers and IaC.
  • Agents and their tools. 13 agent frameworks. Tools are attached to the agents that use them, classified by capability (payment, shell, file write, email) and checked for an approval step.
  • MCP. Static review of server definitions, plus a live probe limited to initialize and */list. tools/call is never sent, and a hard guard enforces it.
  • Model files. Pickle streams are disassembled without being executed; references to code-execution callables are reported with opcode evidence.
  • Shadow AI. Provider usage compared with the organization's approved list — reported as unknown rather than unapproved when no list is set.
  • Red team. 15 deterministic, marker- and canary-based tests inside an authorization, scope, budget and rate-limit envelope. Requested tools are recorded, never run.

Scan a repository in one command

aictem is the platform's discovery CLI. It runs where the code lives — a laptop or a CI job — and inventories a repository from the inside. The Python standard library is its only dependency. 

# nothing to deploy, nothing to configure
pip install aictem && aictem discover .

# for GitHub code scanning, or to send the inventory to the platform
aictem discover . -f sarif -o aictem.sarif
aictem discover . --upload --gate high

It finds AI providers and models, agents and their tools, RAG pipelines, vector stores, MCP servers and clients, model files, packages from 8 ecosystems, container images, Kubernetes, Terraform, CloudFormation, CI pipelines and committed secrets. Model files are never loaded, and a secret's value never leaves the machine — a finding carries the prefix, the length and a fingerprint.

One image to deploy

The role is the command. PostgreSQL, Redis and object storage are external.

docker pull ghcr.io/d0gra/ai-ctem:0.3.0

docker run ghcr.io/d0gra/ai-ctem:0.3.0 migrate   # apply database migrations, then exit
docker run ghcr.io/d0gra/ai-ctem:0.3.0 all       # web, API and worker in this container
docker run ghcr.io/d0gra/ai-ctem:0.3.0 serve     # web and API, with workers elsewhere
docker run ghcr.io/d0gra/ai-ctem:0.3.0 worker    # background jobs only

Released images carry build provenance and an SBOM attestation. Compose and Kubernetes manifests are in the repository; the Kubernetes layout is the same image three times, differing only in its arguments.

What it is not, yet

Worth knowing before you evaluate it. The full list is in the repository's README.

  • No single sign-on. No OIDC or SAML, and no SCIM provisioning.
  • AWS only for native cloud inventory. Azure and Google Cloud arrive through Prowler reports, and there is no live Kubernetes inventory.
  • No web crawler and no injection testing. Passive analysis and safe read-only probes only; bring ZAP, Nuclei or Semgrep and import the results.
  • Attack paths are built from recorded relationships. Network reachability is not computed, so a path can be overstated.
  • Third-party integrations are verified against emulators and recorded API shapes, not yet against real AWS, Jira, GitHub, GitLab, Slack or Teams accounts.
  • Scale is exercised with hundreds of assets per organization; there are no load tests yet.
